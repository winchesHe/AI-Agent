# Feature Specification: Telegram 即时消息入站通道

**Feature Branch**: `005-telegram-im`  
**Created**: 2026-03-22  
**Status**: Draft  
**Input**: User description: "开始实现 IM 的接入，需要接入 Telegram 进行 IM 调用"  
**修订**: 过程可见性不得删减；思考与轨迹/流式进度须在 **Telegram 线程（thread）** 语义下组织（见 US4、FR-010）。  
**修订（工作区范围）**: 部署与日常操作**不限定**「仅能在本仓库根目录作为唯一合法工作区」；操作者常在**用户主目录**（如 macOS 上的 `~`，即 `/Users/<用户名>/`）或项目目录下打开终端，**当前工作目录（cwd）**决定相对路径落点；文件类配置路径的解析规则须在文档中明确（见 Assumptions、FR-011）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 通过 Telegram 与助理对话 (Priority: P1)

作为已部署本助理的使用者，我希望在自己常用的 Telegram 客户端中向机器人发送**文本消息**，助理能像本地 CLI 任务模式一样理解意图并返回**文本回复**；单次对话在文档声明的超时与迭代预算内完成，失败时我能看到**可理解的说明**而非无响应。

**Why this priority**: 无收发闭环则 IM 接入无验收意义，是所有后续能力的基础。

**Independent Test**: 使用测试用机器人账号，从已授权对话发送一条简单问答与一条需多步推理/工具的任务，确认均能收到回复且内容与 CLI 同类任务语义一致（允许表述差异）。

**Acceptance Scenarios**:

1. **Given** 通道已按文档完成启用且凭证有效，**When** 用户发送一条纯文本问题，**Then** 用户在合理时间内收到助理的文本回复。
2. **Given** 助理执行超过单次预算或依赖的外部能力失败，**When** 本轮处理结束，**Then** 用户收到说明原因或降级结果的文本，且行为符合全局轨迹/日志策略。
3. **Given** 用户连续发送多条消息，**When** 每条消息独立处理，**Then** 每条均有对应回复（不要求跨消息记忆，除非产品其他规格已声明会话级上下文）。

---

### User Story 2 - 与既有入站安全策略一致 (Priority: P2)

作为关注安全的操作者，我希望 Telegram 来源在系统中具有**可识别的来源标识**，并与现有「未配对来源对敏感能力默认拒绝」策略**兼容**：仅当来源已完成配对（或全局策略为允许）时，敏感插件/子代理方可被该消息触达；未授权时不应静默失败到无法诊断。

**Why this priority**: 与 004 个人助理规格中的不可信入站叙事一致，避免 IM 成为权限绕过面。

**Independent Test**: 配置至少一个敏感插件标识，未配对用户发送会触发该插件的消息时收到明确拒绝或引导；完成配对后同等消息可通过策略校验（若业务允许）。

**Acceptance Scenarios**:

1. **Given** 安全策略为默认拒绝且某插件标记为敏感，**When** 未配对来源发起将触发该插件的请求，**Then** 用户侧收到不泄露内部实现细节的提示，且轨迹/日志可区分「策略拒绝」与「模型/工具错误」。
2. **Given** 操作者按文档将某 Telegram 用户完成配对，**When** 该用户再次发起同类请求，**Then** 行为与文档声明的授权范围一致。

---

### User Story 4 - 运行过程可见、减少「长时间无反馈」(Priority: P1)

作为 Telegram 用户，我希望在助理处理一条消息时**持续看到两类进度**（**不得**因产品改版而改为「仅终稿、无过程」）：一是与 OpenClaw 对齐的**轨迹步骤摘要**（思考摘要、工具名与结果等）；二是在每一轮模型生成时，在 API 允许的前提下看到**该轮模型输出的逐步累积**（而非整段生成结束前进度区完全静止）。上述**思考与过程内容**应出现在 **Telegram 的回复线程（thread）** 中：系统为每轮用户问题**建立可识别的线程上下文**（以用户入站消息或首条机器人占位/确认消息为**线程锚点**，私聊与群/论坛场景以实现文档为准），在该线程视图内增量展示过程；**同一线程内**可采用**单条进度消息的多次编辑**，或**多条回复串联至同一线程根**，以实现文档与平台能力为准。**最终可见回答**仍单独呈现（可与过程同线程，便于与思考区段区分），不得与「取消过程展示」相绑定。

**Why this priority**: 多步 ReAct / 工具调用可能耗时数十秒；无过程反馈会被误认为卡死或掉线；线程化便于在客户端中折叠/展开「思考」与「结论」。

**Independent Test**: （1）发送一条会触发至少两轮「思考 + 工具」的任务，确认在最终回答到达前，在**对应回复线程内**出现**可更新的进度文本**（轨迹与步骤语义一致，允许截断）。（2）发送一条**单轮即可完成**的纯文本推理题，在 quickstart 所声明的流式友好环境下，确认**线程内**进度出现**多于一次**的可见变化（含轨迹与/或当前步模型累积文本，允许因网关缓冲呈块状更新）。

**Acceptance Scenarios**:

1. **Given** 通道已启用且请求会触发多步循环，**When** 模型或工具执行进行中，**Then** 用户在合理延迟内、于**本轮对应的线程内**看到至少一条非空的进度更新（例如思考摘要、工具名或状态提示）。
2. **Given** 本轮正常结束，**When** 最终回答发送前或同时，**Then** 用户能区分「过程已结束」与「最终可见回答」（不要求单一消息内混排全文，但须避免长时间零反馈；**优先**在同一线程或清晰关联的回复链中呈现）。
3. **Given** 本轮因错误提前终止，**When** 处理结束，**Then** **线程内**进度或后续关联消息中能反映失败或未完成状态（不泄露密钥等敏感配置）。
4. **Given** 所用模型端点支持流式补全且未被中间层完全缓冲，**When** 某一 ReAct 步正在生成模型回复，**Then** 用户在**线程内**进度展示中能在该步结束前看到**当前步输出的累积增长**（更新频率以实现侧节流与平台限制为准，不保证严格逐字）。

---

### User Story 3 - 可配置、可诊断上线 (Priority: P3)

作为部署者，我希望通过**配置文件或环境变量**启用/停用 Telegram 通道，并在误配（令牌缺失、网络不可达等）时得到**启动阶段或自检阶段**的明确错误信息；文档提供从零到收到首条回复的最短路径。

**Why this priority**: 降低接入摩擦，减少「黑屏无日志」类运维问题。

**Independent Test**: 故意缺失必选密钥时进程拒绝进入收消息状态并打印可检索错误码或字段名；按 quickstart 全流程可在新环境复现首条往返消息。

**Acceptance Scenarios**:

1. **Given** 未提供通道所需密钥，**When** 启动收消息模式，**Then** 启动失败并提示缺失项，不进入假装可用的空转状态。
2. **Given** 配置正确，**When** 操作者执行文档中的自检或健康步骤，**Then** 能确认通道组件已加载（具体接口形态以实现为准，但须文档化）。

---

### Edge Cases

- Telegram 服务不可用或超时时，助理是否重试、是否向用户发送临时提示？须在实现文档中约定，且不应无限重试耗尽资源。
- 用户发送非文本消息（图片、贴纸、命令等）时的默认行为：明确拒绝、固定提示或忽略之一，并写入文档。
- 极高并发或单用户刷屏时，是否排队、丢弃或限速：须有默认策略与可观测信号（如日志计数）。
- **同一故障场景下，用户侧不得出现两条语义重复的错误气泡**（例如先编辑进度消息为错误提示、再单独回复同文案）；实现应合并为单次可见反馈，仅在进度编辑失败时再回退为单独回复（见 plan / quickstart）。
- **线程不可用或客户端不展示话题**：部分旧版群组或聊天类型可能无「话题/线程」UI；实现 MAY 退化为**回复链锚点**（`reply_to` 语义）或会话内单链进度，**仍须**满足 FR-008 / FR-009 的增量过程，不得以无线程为由改为仅终稿。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持将 Telegram 用户发送的**文本消息**投递给既有助理执行管线，并将最终可见结果以**文本形式**回复至同一会话。
- **FR-002**: 系统 MUST 为每条入站 Telegram 消息构造稳定的**来源标识**，以便与配对存储及安全策略对照。
- **FR-003**: 系统 MUST 尊重既有「默认拒绝 + 敏感插件需配对」策略；在未授权访问敏感能力时 MUST 向用户给出明确、安全的提示。
- **FR-004**: 系统 MUST 支持通过配置启用或停用 Telegram 通道；停用时不应建立对 Telegram 网络的长连接或轮询（除非文档声明的惰性探测另有说明）。
- **FR-005**: 系统 MUST 在启动或自检路径上对必选配置进行校验；校验失败时 MUST 阻止进入收消息就绪状态。
- **FR-011**: 系统 MUST 在运维文档中说明：凡配置中的**文件路径**（如配对库、可选日志文件）若以**相对路径**给出，则相对于**该次进程启动时的当前工作目录**解析；**不**隐含「路径始终相对某一固定代码仓库根」。典型情况下终端默认 cwd 为**用户主目录**（`~`），相对路径会落在该目录树下；若希望日志/配对库落在**项目仓库内**或**固定绝对位置**，SHOULD **`cd` 到目标目录再启动**或在 YAML 中使用**绝对路径**。
- **FR-006**: 系统 MUST 提供操作者可执行的**配对管理**能力（例如命令行或受控管理接口），用于将 Telegram 用户标识登记为已配对来源。
- **FR-007**: 系统 SHOULD 将通道侧错误与助理执行错误区分记录，便于排障（不要求用户可见区分，但运维可见）。
- **FR-008**: 系统 MUST 在 Telegram 文本对话路径上，将助理运行过程中产生的**轨迹步骤摘要**（与既有 trace 语义对齐，如思考、工具调用/结果、错误）以用户可读形式**增量展示**，使多数多步任务在获得最终回答前至少出现一次进度更新；展示 MUST 落在 **FR-010 所定义的线程（或等效回复链）上下文内**，不得仅发到与本轮问题无关联的平铺消息流而使用户难以关联「思考」与「提问」（除非平台能力限制且已在 quickstart 声明降级形态）。
- **FR-009**: 系统 MUST 在 Telegram 文本对话路径上，在底层模型客户端支持流式补全的前提下，对 **Agent Loop 内每一次模型调用**采用**流式消费**，并将**该步模型输出的累积文本**与 FR-008 所述内容通过**同一线程内的进度载体**增量展示（例如该线程中**同一条消息的多次编辑**，或等效的多消息串联，以实现文档为准）；若端点或网关仅提供非流式整段响应，MAY 降级为该步生成结束后单次更新，且须在 quickstart 中说明现象与可选缓解（例如部署文档中的客户端平滑参数）。流式展示的**时间粒度**受 API、网络与 IM 平台编辑频率限制，规格**不**要求严格逐字均匀到达。
- **FR-010**: 系统 MUST **保留** FR-008 / FR-009 所要求的**全过程增量展示**，不得以「改为 thread 布局」为由移除或显著削弱过程可见性（**不得**退化为仅发送无过程终稿）。系统 MUST 在 Telegram 能力与聊天类型允许的前提下，为每轮用户文本入站**建立可识别的回复线程（thread）语义**：以用户消息或本轮首条机器人消息为**锚点**，使**思考与进度**出现在该线程视图内（实现可依赖论坛群的 `message_thread_id`、普通私聊/群组的**回复链**等；具体 API 形态写入 plan / quickstart，**不**在规格中绑定单一字段名）。**最终回答** SHOULD 与过程**同线程**或**明确回复到同一线程根**，以便用户折叠「思考」、阅读「结论」；若产品选择将终稿置于会话顶层，MUST 在 quickstart 说明客户端中的查看方式。

### Key Entities

- **入站来源**: 抽象为「通道类型 + 发送方标识」；Telegram 场景下发送方标识应能唯一区分对话发起方（例如用户数字 ID）。
- **配对记录**: 与既有规格一致，记录某来源已被授予的信任级别及配对时间。
- **通道配置**: 启用开关、凭证引用方式（不明文落盘密钥本身）、可选连接模式等与 Telegram 对接相关的非密钥元数据。
- **线程锚点（一轮对话）**: 用于绑定「用户问题 ↔ 思考进度 ↔ 终稿」的 Telegram 消息或话题标识；随聊天类型不同，语义上对应「回复线程根」或「论坛话题」等。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在实验室网络下，配对完成的测试用户在发送文本后 **60 秒内**收到首条回复的成功率不低于 **95%**（排除故意的 LLM/外部 API 故障用例）。
- **SC-002**: 新部署者按 quickstart 文档，**30 分钟内**可完成从配置到首条成功往返消息（含一次有意误配后的纠正）。
- **SC-003**: 未配对来源触发敏感插件的请求中，**100%** 在用户侧得到非空提示或在日志中有可检索的拒绝记录（二者至少满足其一且文档说明以何为准）。
- **SC-004**: 关闭通道配置后，系统在 **5 秒内**停止新的 Telegram 收消息处理（已进行中的请求允许在文档声明的上限内结束）。
- **SC-005**: 在实验环境下，针对会触发 **≥2 条**轨迹步骤（不含纯启动占位）的测试用例，**90%** 以上在最终回答送达前，用户侧已收到至少 **1 次**进度文本更新（以消息编辑或追加为准；**验收时进度须落在本轮对应的 thread / 回复链上下文中**，具体形态以实现文档为准）。
- **SC-006**: 在 quickstart 声明的**流式友好**实验配置下，针对**单轮即可完成**的纯推理样本，**80%** 以上在最终回答送达前，用户侧进度展示出现**至少 2 次**可区分的文本变化（含首次占位、轨迹更新与/或当前步模型累积更新，以手工清单步骤为准；**同上，须在 thread / 回复链上下文中**；网关缓冲导致块状到达视为有效）。

## Assumptions

- **本机工作区语义**：操作者的「工作区」常为**用户主目录**（`~`）或**项目仓库根**，二者**不**自动等同。相对路径类配置一律相对**进程 cwd**（从家目录启动时，`logs/hello-agent.log` 会出现在 `~/logs/...`，而非仓库内）；与「先 `cd` 到仓库根再执行 `telegram run`」的推荐流程并存，或由部署者在 YAML 中写**绝对路径**（例如指向 `~` 下某固定子目录）以稳定落盘位置。
- 首期以**文本消息**为主；富媒体与内联键盘等可作为后续特性。
- 凭证通过**环境变量或配置中的变量引用**提供，不以明文密钥写入版本库。
- 助理核心执行模型与循环预算与当前仓库已实现行为一致，本特性主要增加**入站适配与回传**。
- **流式体验**依赖模型服务端是否真实下发分块响应；部分企业网关会缓冲 SSE，用户侧可能仍表现为「少次大块」更新，与 FR-009 的 MAY 降级一致。
- 若部署者启用**本地文件日志**，实现约定：**控制台**仍遵循配置的 `logging.level`；**日志文件**仅持久化 **ERROR 及以上**（含 `logger.exception` 栈），以减少噪声；日志目录**不入版本库**（见 `plan.md` / `quickstart.md`）。
- **Thread 呈现**依赖 Telegram 客户端与聊天类型（私聊、普通群、论坛群）；规格以**用户可理解的「折叠式思考区 + 结论」**为目标，具体 API 组合以实现为准。
